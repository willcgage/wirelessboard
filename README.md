<h1 align="center">Wirelessboard</h1>

A visual monitoring tool for network enabled Shure devices.  Wirelessboard simplifies microphone monitoring and storage for artists, engineers, and volunteers.  View battery, audio, and RF levels from any device on the network.

> Wirelessboard is the new name for the project previously released as **Micboard**.  Existing configurations, environment variables, and automation targeting Micboard continue to work, and migration tips are documented throughout this repo.

## Screenshots

#### The board
Each card is built around the photograph of whoever is holding that microphone, and the photo is
never printed over. Above it sits the transmitter's own label and the position being filled this
service — `HH-07` and `Electric` are different facts and change independently. The band underneath
carries the status colour and the person's name. Below that: the audio and RF levels with a short
trend beside each, the battery and the time remaining, then the frequency, the transmitter offset
and the receiver's link quality.

The amber card needs its transmitter replaced and the red one is nearly flat — the battery takes
the colour of the state it is in, and flashes once it is critical. `NO TX` is a receiver with
nothing switched on, which is why its battery is an outline rather than an empty cell: the board
says "nothing has told us" rather than "about to die".

## Compatible Devices
Wirelessboard supports stage wireless systems — handheld and bodypack transmitters on a rack receiver, and in-ear monitor transmitters. Conferencing systems are not supported.

| Device | Notes |
| --- | --- |
| Shure Axient Digital | AD4D / AD4Q |
| Shure ULX-D | |
| Shure QLX-D | See [QLX-D Firmware](docs/qlxd.md) |
| Shure SLX-D+ | Up to four channels |
| Shure SLX-D | <sup>[1](#slxd)</sup> Third-party control is **off by default** on the receiver |
| Shure UHF-R | |
| Shure PSM 1000 | In-ear monitor transmitter |

Wirelessboard uses IP addresses to connect to RF devices.  RF devices can be addressed through static or reserved IPs.  They just need to be consistent.

SLX-D and SLX-D+ do not appear in network discovery yet — add them by IP address on the configuration page.


## Key Features

* **A wall of faces.** Each channel is a card built around the photograph of whoever is holding that
  microphone — the radio and what the slot is for at the top, their name and time remaining in a band
  along the bottom. The photo is
  never printed over or dimmed. Stills (`.jpg`, `.png`, `.webp`) and muted looping video (`.mp4`,
  `.mov`) both work, matched to the channel's name or chosen per person — see the
  [configuration guide](docs/configuration.md#background-images).
* **Everything is reachable by tapping.** The board is worked from two menus: a gear in the corner
  for everything about the screen in front of you, and the Menu for everything that changes every
  board. It runs on wall tablets and phones, which is why there are no keyboard shortcuts.
* **Status you can read without seeing colour.** A channel needing attention carries a badge reading
  "Replace", "Low" or "RX error" beside its symbol, not just a colour — red and amber are the two
  states that matter most and the two hardest to tell apart, especially over a photograph.
* **Time remaining on every channel.** Where a receiver reports only a battery level, Wirelessboard
  works the remaining time out from how fast that level is falling, and marks it as an estimate. It
  says nothing rather than guessing when there is not enough to go on.
* **Planning Center Services.** Sync who is on which microphone straight from the week's plan, with
  a preview that shows what will change on *your board* — who is on each slot now, who would be
  after — before anything is written. Rule sets handle different kinds of service, and the board can
  tell you when the plan changes mid-morning.
* **Built for a wall.** Cap how many columns the board uses, page through groups on a timer when
  there are more channels than fit, and lock a tablet to display only so a stray tap cannot reach
  the configuration.


## Photographs of the team

The board is a wall of faces, so the photographs do more work than anything else on it. Wirelessboard
will never cut a face off — a picture that does not match the card is shown whole, with the space
around it filled by a blurred copy of itself — but a photograph taken for the shape of the card needs
no filling at all, and looks considerably better.

**A channel card is always taller than it is wide, often much taller.** That single fact drives
everything below.

| | |
|---|---|
| **Shape** | Portrait, about **3:4 or 4:5**. 1200×1600 is ample. A phone held upright is already right. |
| **Crop** | Head and shoulders, with the face filling roughly **a third of the frame's height**. |
| **Framing** | A little headroom, person near the centre. A head against the top edge is the first thing a short card loses. |
| **Subject** | One recognisable face, looking toward the camera. |
| **Light** | Even and front-ish. |

What to avoid, and why:

* **Wide stage shots.** A 16:9 photograph in a card a fifth as wide as it is tall is the hardest case
  there is. Nothing is cropped away, but the picture sits small inside a blurred band.
* **Full-length shots.** The face ends up a few pixels across on the wall, which defeats the point.
* **Profiles, backs of heads, and faces behind a microphone or a cymbal.** These read as nobody from
  five feet away, and no amount of scaling fixes a face that is not in the frame.
* **Backlit stage lighting.** A silhouette cannot be brightened back into a person.

Photographs taken on a phone keep their rotation, so an upright shot stays upright.

> **One arrangement matters as much as the photographs.** With twelve channels in a single row every
> card is a narrow strip whatever the picture. **Grid** is the arrangement photographs are at their
> best in.

What a file must be called for a channel to find it is a separate matter — see
[background images](docs/configuration.md#background-images), or the Backgrounds pane, which lists
the exact filename each slot is looking for.

### Live development workflow

Wirelessboard now ships with a watch-based workflow that keeps the Python server and compiled assets in sync while you work:

1. Install dependencies if you haven't already: `npm install`
2. Start the dev environment with `npm run dev`
  * Webpack runs in watch mode, rebuilding the bundles on every change.
  * `nodemon` restarts the Python server whenever the generated `static/` assets, templates, or files in `py/` change, so a browser refresh shows the latest UI without a manual server restart.

Press `Ctrl+C` to stop both processes. The traditional one-shot build (`npm run build`) and manual server start (`npm run server`) still work for production-style testing.

### Python dependency lockfile

Python packages live in `py/requirements.txt`, and a fully pinned snapshot is tracked in `py/requirements.lock`. Installations should prefer the lockfile for repeatable builds:

- `pip3 install -r py/requirements.lock`

When dependencies change, update both files by reinstalling into the project virtualenv and running `npm run pip:lock`. The helper script regenerates `py/requirements.lock` using the current virtualenv so releases and CI pick up the new pins.

### Versioning and releases

Wirelessboard follows [Semantic Versioning](https://semver.org/) for Git tags, desktop bundles, and the Raspberry Pi tarball. The `npm version` command keeps all metadata in sync and prepares a release tag:

1. Choose the appropriate bump (`patch`, `minor`, or `major`) and run `npm version <level>`.
  * This updates `package.json`, regenerates `py/version.py`, commits the change, and creates a Git tag such as `v1.0.1`.
2. Push the commit and tag with `git push --follow-tags` to trigger the release workflow.

The GitHub Actions workflow builds platform installers named with the new version, and Raspberry Pi bundles now include the semantic version in their filename.

> ℹ️ The desktop packaging scripts auto-detect a Python interpreter. If your system does not expose `python` or `python3` in `PATH`, create the project virtualenv via `npm install` or set `WIRELESSBOARD_PYTHON` to the interpreter you want PyInstaller to use. GitHub Actions removes the temporary `.venv` after bundling to avoid packaging symlinks; set `WIRELESSBOARD_KEEP_VENV=1` if you need to retain it in custom CI.


## Known Issues
<a name="qlxd">1</a>: [QLX-D Firmware](docs/qlxd.md)

<a name="slxd">1</a>: SLX-D and SLX-D+ block third-party control by default. On the receiver, go to **Advanced Settings → Controller Access** and allow it, otherwise Wirelessboard connects but the channel never reports anything. These models also do not report antenna, channel quality, transmitter offset or power lock — those parts of the info drawer stay empty, which is the receiver rather than a missing feature.
